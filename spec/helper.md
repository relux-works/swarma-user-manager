## 1. Purpose

Figure [M-UM1: privileged components and process boundaries](../diagrams/components.puml) maps the responsibilities below; it describes the design, not implemented components.

An agent system gets a real boundary between agents on one machine by running each agent under its own OS account: processes of different accounts cannot read each other's files or memory, and kernel firewalls can match traffic by account. Creating accounts, starting processes under them and installing firewall rules need root. This repository holds the privileged account and launch components, and each holds its power narrowly:

- **swarma-user-manager** creates, lists and retires accounts, owns the static range deny from v0 and (v1) applies per-account firewall rules;
- **swarma-user-launcher** starts one approved executable under one active agent or qualified workplace account.

Both run as root for one operation at a time, are invoked through `sudo` by configured callers (launcher: dispatchers only), accept only operations from closed, versioned schemas, choose names and identifiers themselves, act only on what they manage, journal their steps, and serialise protected transitions on one lock, yielding between bounded retirement batches (§4.6).

### 1.1 Non-goals

- They do not decide who may start an agent (the dispatcher does) and do not hold credentials (the broker does).
- The helper never starts processes; the launcher never creates accounts or rules.
- Neither accepts free-form commands, paths, shell fragments or environment.
- Donor provisioning and removal belong to a **separate donor-side provisioning component**, with its own short specification, rules, removal contract, binary and privileges (D-DONOR-PROVISIONING). It MAY share UID and path-checking libraries, but is not a helper operation. Neither `create-worker` nor `remove-worker` is supported by this helper, and `user.create`/`user.retire` are not substitutes for donor provisioning. Donor variant B stays disabled until that component is specified.

## 2. Invocation

- Each binary is installed at a fixed root-owned path, is not setuid, and every directory on its path is root-owned and not writable by others.
- Each sudoers rule allows a configured caller (launcher: dispatchers only) to run exactly that path **with no arguments**, using the empty argument specification, for example `swarma-dispatcher ALL=(root) NOPASSWD: /opt/swarma/libexec/swarma-user-manager ""`. The binaries also refuse any argument (`argv_not_allowed`). The R-ALLSTOP operator exception initiates helper containment/stops through this authenticated terminal boundary without the dispatcher (§§3, 4.7, 8.3); it supplies no general command or launcher access.
- `NOPASSWD` MUST be confined to the dispatcher service account's helper and launcher rules. The helper rule for the `operator` UID (`swarma-operator`, §3) MUST require authentication and MUST set `timestamp_timeout=0`; a cached sudo ticket cannot authorise another act. Installer helper rules also require authentication. The terminal fallback into `swarma-operator` requires a password, no `NOPASSWD` and `timestamp_timeout=0` (§11). The authenticated phone-to-helper transition would need publication and qualification (§14, question 17); phone SSH authentication alone does not define a sudo mechanism or permit an unauthenticated helper rule.
- The binary refuses unless its effective UID is 0 (`not_root`) and `SUDO_UID` is present and a plain decimal number (`not_invoked_by_sudo`). `SUDO_UID` is the caller's identity only because sudo set it during a trusted transition; it is not proof of the caller's executable, and root callers are outside this boundary.
- The binary clears its environment, sets a fixed `PATH`, working directory and umask, and calls operating-system tools only by absolute path, never through a shell.
- The request is exactly one JSON document on stdin, read within 5 seconds: at most 16 KiB for `swarma-user-manager helper-op/1` and 80 KiB for `swarma-user-manager launch-op/1` (`request_too_large`, `request_timeout`). Duplicate keys, unknown members, a trailing document, strings longer than their declared bound and arrays longer than theirs are refused (`request_invalid`).
- The answer is one JSON document on stdout; diagnostics go to the audit log.

```
swarma-user-manager helper-op/1
{ v: 1,
  op:         "user.create" | "user.retire" | "user.list" | "effect.observe" | "exec.stop" | "archive.sweep" | "fw.apply" | "fw.remove",
  request_id: string (≤ 64),           // mutation: caller-scoped effect key; read: correlation, §§4.6, 5
  args:       { … per operation … } }

swarma-user-manager helper-result/1
{ request_id, ok: true, result: { … }, state: current state of the target }
| { request_id, ok: false, error: { code, message } }
```

`effect.observe` is a read-only operation in `helper-op/1` (R-OBS). Its arguments identify the original effect's `request_id`, operation and digest of its canonical arguments; the outer `request_id` remains request correlation and does not admit a new effect. The exact argument/result member encoding and canonical digest bytes are unpublished (§14, question 8); no additional wire fields or refusal codes are assigned here. Its observation result is exactly one of:

| Observation state | Evidence / result |
|---|---|
| `recorded` | Recorded result together with the target's current generation/state |
| `pending` | The original effect is recorded but unresolved |
| `rolled_back` | Authoritative journal evidence that this attempt was rolled back |
| `not_recorded` | Complete authoritative evidence that this effect was never recorded |
| `unavailable` | Evidence is missing, expired or unreadable; never evidence of absence |
| `contradictory` | Authoritative evidence conflicts |

Only the original caller principal and configured operators may observe an effect. Observation is serialized with the receiver journal (§§4.5–4.6), including launch/stop evidence held by this module. It neither renews mutation authority nor performs a new mutation; it remains available to that authenticated principal after its mutation grant expires. Evidence retention and the absence boundary are specified in §4.6.

A `grants` member is refused until v2 (`grants_unsupported`), so an ignored grant can never look verified.

Versioned wire identifiers follow `swarma-<component> <object>/<n>`, using the **repository** name (D-WIRE-NAMES). Both binaries belong to `swarma-user-manager`; their request kinds above and the result kind therefore use that prefix. Nothing has shipped, so no migration is needed. These are this module's existing request/result schema-kind identifiers, not signed-request domains or a signature grammar (§9). Short transport/schema labels owned by other modules stay unchanged. Signing domains, kind discriminators, transport/schema labels and provisional design labels are separate categories; this module does not derive a prefixed replacement for another owner's label. The cross-module D-WIRE-NAMES scope clarification and typed index remain contract-owner publication work (§14).

| Message or payload | Maximum size | Intake / owner |
|---|---|---|
| Helper request (`swarma-user-manager helper-op/1`) | 16 KiB | One JSON document on stdin, 5 seconds; this section |
| Launcher request (`swarma-user-manager launch-op/1`) | 80 KiB | One JSON document on stdin, 5 seconds; §§2, 7 |
| Plan within launcher request | 48 KiB decoded; 64 KiB base64 | Delivered decoded on descriptor 3; §7 |
| Dispatcher service frame | 128 KiB | Dispatcher §10 |
| Broker frame | 64 KiB | Broker §13.1 |

The dispatcher MUST refuse a payload exceeding the smallest bound on its launch path before provisioning. The dispatcher frame limit does not enlarge the launcher's request or plan bounds.

## 3. Policy

A root-owned configuration lists callers by UID and gives each a role:

| Role | May |
|---|---|
| `installer` | create and retire **service** accounts it names in the configuration; apply/remove their v1 service-profile rows (§8); run `archive.sweep`; observe its own effects |
| `dispatcher` | create agent and qualified workplace accounts up to its quota; retire, launch and apply rules only for those accounts **it created** (`created_by` = its principal); stop its executions; observe its own effects |
| `operator` | UID of `swarma-operator` only; all helper operations, including retiring protected service accounts and the R-ALLSTOP range-deny-all act, subject to per-act authentication/content confirmation below; observe effects from any principal; no launcher authority; R-ALLSTOP receipt-backed stops/never-launched absence use §8.3 |

Requests outside the caller's role are refused (`caller_role_not_permitted`, `target_not_owned`, `quota_exceeded`). Only configured dispatchers may invoke `swarma-user-launcher`; installer, operator and session-host principals have no launch sudo rule or launcher role. Configured dispatchers are trusted administrators of their own agents; until v2 (§9) the policy is the authority.

**Operator custody (R-OPERATOR).** `swarma-operator` is a separate protected service-class account that MUST NOT host a harness session. It is the configured broker operator and account owner, the user manager's `operator` UID, and the holder of operator signing authority, including the broker v0 root and records for `team/1`, standing retirement, maintenance authority, explicit home retention and standing re-grants. The person's interactive account is not this principal and holds no operator signing authority. `swarma-observer` is a mandatory protected service-class read-only account that also MUST NOT host a harness session. Human reads of status, grants, accounts and bindings go through it without confirmation; it has no operator mutation or launcher authority. It can read the public ledger (§4.5); the other read interfaces and their access boundary would need joint publication (§14, question 17). This does not give it another principal's private `effect.observe` journal access (§2).

Widening operator acts require authentication **plus confirmation of the exact act's content**: grant issue, subscription enrolment, `team/1`, standing retirement or re-creation, explicit home retention, maintenance stop authority and renewal of standing grants. The operator CLI MUST refuse operator acts from inside agent sessions, including R-ALLSTOP. Narrowing acts (revocation and disabling an account) require authentication only, except R-ALLSTOP requires authentication and one confirmation of the node-wide act (§8.3). Reads through `swarma-observer` require no confirmation. These human gates do not remove admitted dispatcher/service narrowing authority or grant an automatic widening path. Operator renewal/re-grants and maintenance authority remain human-presence acts; unattended widening cannot be inferred from an old confirmation or cached ticket. The phone and terminal entry paths are defined in §11.

**Admission class (R-UNTRUSTED).** The class is recorded at registration or admission, never inferred from an account name. Remote workers (donors and freelancers) come first; every workplace allocation is untrusted-class unless the operator admits that remote worker to the trusted circle by an operator act at admission, and later any identity the operator classifies as untrusted joins it. Slice 0 and user-manager v0 refuse to activate it; the refusal code and class encoding are unpublished. v1 admission requires the host's qualified capability matrix to meet class minimums (R-CEILINGS), zero workplace egress and never `direct` (R-NET-TOOL), an OS-enforced exec profile (R-EXEC), no subscription binding or lease ever (the broker refuses both), no local agent loop (R-STANDING), and no shared services on the host (R-SHARED). Trusted-circle membership enables only donor-side opt-ins such as web search (§8); it never relaxes zero workplace egress, the exec profile, the transfer path or review on our host. Missing or unknown qualification closes admission. No OS is excluded by name.

Workplace creation/launch is admitted only under the jointly published backend and these class gates (§§4.3, 7–8, 14). Service-profile rules use installer/operator authority; a dispatcher cannot alter a service row. The closed service-profile/deny-all argument encoding would need publication (§14, question 12); this role extension invents no wire members.

## 4. Accounts

### 4.0 Layout

Figure [M-UM4: storage layout and owners](../diagrams/storage-layout.puml) expands this tree, including OS records and the launcher descriptor boundary.

```
/opt/swarma/                 root 0755
  libexec/                   root 0755: protected platform binaries
    swarma-user-manager      v0 accounts; v1 egress adapter
    swarma-user-launcher     v0 one-shot launch; dispatcher caller only
    swarma-dispatcher        Unix-socket service from its first slice
    swarma-credential-broker v0 broker daemon / CLI
    swarma-session-host      SH2+ service-account host (activation gated)
    swarma-session-runner    SH2+ agent-account runner (activation gated)
  etc/                       root 0755: user-manager.json (policy, ranges, metadata retention), approved-executors.json
  lib/user-manager/                root: ledger.json (0644), receipts/ (0644 files), applied-state/ (0644), journal/ and lock (0700)
  run/                       service socket directories, 0755
    credential-broker/      v0
    dispatcher/             first dispatcher slice
    session-host/           SH2+ (activation gated)
  services/<account>/        homes of service accounts, 0700
  workers/<account>/         homes of agent and workplace accounts, 0700 (work/, tmp/ and harness state inside)
  quarantine/                root 0700: homes moved here for retirement deletion
  archive/                   root 0700: closed-schema service-generated metadata exports; files root 0600
```

The root is chosen at installation (for example on a separate volume); every path below is relative to it. The machine-owned network binding policy lives beside `etc/user-manager.json`; its filename and encoding remain unpublished (§8, R-NETBIND).

These phases identify each component's platform placement, not a shared release number. The dispatcher is an unprivileged Unix-socket service from its first slice, using the broker's connection/framing rules; its service entry point does not use stdin command requests. It still invokes the helper and launcher through sudo as their root-helper caller. SH1 extraction of the session host does not activate its SH2+ service-account layout. Companion components own their binaries and socket contracts; the helper/launcher installer scope remains §11.

### 4.1 Names and identifiers

- Agent and workplace accounts are named `worker-<label>`, where the label is usually the profile and a short id (`worker-dev-7f3`); service accounts are named `swarma-<name>` (owner decision 2026-10-10). Both stay within the 32-character limit of Linux user names. `label` and `name` MUST match `[a-z0-9][a-z0-9-]{0,22}` (`label_invalid`).
- UIDs and GIDs come from configured ranges: agents and workplaces 30000–59999 on both systems; services 450–499 on macOS and 900–999 on Linux. Agents and workplaces are hidden from login windows by attribute, services by range.
- **Allocation is round-robin:** the helper keeps a cursor in its ledger and takes the next value after the last one it issued that is free in the directory service and in its ledger, wrapping at the end of the range. A value is reused only after a full cycle, and only when no file owned by it remains under the platform root, in the system temporary directories and in the account's per-user temporary area (`uid_not_clean` otherwise). The helper never accepts a UID from the caller.
- Each account gets its own primary group with the same name and number and no supplementary groups.
- Each creation gets a **generation** from a fresh cryptographically random 128-bit value (R-GEN), never a durable counter. It is never reused even when the UID or label is. Known collisions are reallocated before intent; entropy failure admits no creation. Examples use 32 hexadecimal digits for illustration, without prescribing an additional wire format.
- An incomplete retirement retains its UID/GID reservation, quota charge and generation evidence across batches. UID hygiene checks cannot skip a pending reservation or treat a failed scan as clean. Allocation validates shared identity/accounting first (§4.6), without finishing an unrelated, safely classified retirement.

### 4.2 Lifecycle

Figure [M-UM3: account lifecycle](../diagrams/account-lifecycle.puml) shows the creation rollback and retirement commit point. The sequences are in [M-UM2: provision, retire and recovery](../diagrams/provision-retire-recovery.puml).

```
creating → active → retiring → removed
    └─ (failure) → rolled back
```

- `creating`: steps are journaled; a failure or crash rolls the creation back.
- `active`: the account exists. Agents and qualified workplaces may use their admitted launch backend (§7); service accounts gain no launcher authority. Workplace activation also requires its enforced-network gate (§4.3). An admitted trusted agent may be bound by the broker; untrusted-class allocations never acquire a subscription binding or lease (§3).
- `retiring`: the commit point of removal. From here the launcher refuses the generation, the broker refuses its leases, and removal only moves forward, resuming after a crash.
- `removed`: the generation stays in the ledger forever.

### 4.3 `user.create`

Figure [M-UM2: provision, retire and recovery](../diagrams/provision-retire-recovery.puml) shows allocation, creation and rollback boundaries.

```
args:   { kind: "agent" | "service" | "workplace", label: "dev-7f3" }
result: { username: "worker-dev-7f3", uid: 30412, gid: 30412, home: "/opt/swarma/workers/worker-dev-7f3",
          generation: "9ac67d3418e04b0aafe89c6d72b54103", state: "active" }
```

Agent and ordinary service accounts have no usable password, no login shell (`/usr/bin/false` on macOS, `/usr/sbin/nologin` on Linux) and no supplementary groups. Creation and activation refuse under the persisted R-ALLSTOP receiver mark; already-issued creates are reconciled behind the closed inventory frontier (§8.3). The home is created empty under a fixed root (agents/workplaces and services have separate roots), owned by the account, mode 0700, through descriptors (§6). The helper refuses when the name or home already exists outside its ledger (`user_exists_unmanaged`, `home_exists_unmanaged`).

The user manager creates `swarma-operator` and `swarma-observer` as protected **service** accounts under the service naming/range rules (§4.1), never agent or workplace accounts. Only a configured installer naming these services in root policy, or the configured operator, may create them; a dispatcher cannot. The installer bootstraps them before pinning their UIDs and provisioning operator authority (§11). Neither account may host a harness session or use the launcher. Neither has password SSH login or an interactive shell. The operator's device-key-only forced entry (§11) is an explicit exception to ordinary service authentication denial; the observer's read-only entry would need publication. Per-platform account/shell/sshd settings for those narrow entries would need publication and qualification (§14, question 17), rather than claiming the ordinary non-login shell admits an SSH forced command.

- **macOS:** records are created with `dscl` in the local node (`UniqueID`, `PrimaryGroupID`, `UserShell`, `NFSHomeDirectory`, `IsHidden`, a disabled password), not with `sysadminctl`, so that no FileVault or secure-token prompt can occur; ordinary agents/services cannot unlock the disk or log in; narrow operator/observer entries follow the qualification gate above and confer no graphical login or disk-unlock authority.
- **Linux:** the ordinary agent/service backend uses `groupadd` and `useradd` with explicit `--gid`, `--uid`, `--home-dir`, `--no-create-home`, `--shell /usr/sbin/nologin` and a locked password, with distribution defaults that would create extra state disabled; the home is created by the helper.

Qualification verifies each OS/class: agent/ordinary-service authentication disabled; operator device-key-only forced entry and observer read-only entry admit no interactive shell or harness; workplace password disabled and only its qualified certificate-authenticated SSH relay admitted; no elevated/supplementary groups, exact UID/GID/home/shell fields, and service operation without graphical login.

**Persistence denial.** Agent and workplace accounts MUST be denied cron and at through `cron.deny`/`at.deny`. Linux qualification also requires no lingering, no `systemd --user` manager and no automatically created session scope that defeats the selected fate policy. macOS qualification must establish that an agent/workplace UID cannot bootstrap a background `user/<uid>` launchd domain. These are qualification rows, not claims derived from hidden-account attributes. `setsid`, double fork and `nohup` remain covered by account-wide termination (§4.7).

**Workplace (R-WORKPLACE).** Every workplace is untrusted-class unless the operator admits that remote worker to the trusted circle by an operator act at admission (§3). That membership enables donor-side opt-ins only and never relaxes host boundaries. Every workplace requires qualified zero egress, ceilings, exec restrictions and the R-SHARED deployment gate; it is admissible only after helper v1 on that host. Its password is disabled and it has no supplementary groups. Its login shell is a fixed root-owned relay stub under `libexec/`, accepting only sshd's `-c <forced command>` entry and reading no worker-controlled startup file. It relays to a peer-authenticated service Unix socket. The project-side executor `swarma-rb-exec` runs under a service principal, never under the workplace UID; policy, caps, claims, audit and user-CA custody remain outside that UID. The service authenticates kernel peer UID against the active generation. The approved stub identity/grammar, service principal/socket, CA custody and job/runner concurrency policy would need joint publication (§14, question 11); `swarma-rb/1` and `swarma-workplace-exec/1` stay unpublished. v0 cannot activate a workplace. v1 activation requires denial and verified `fw.apply` applied state in the same locked activation transition (§8), including zero egress with no proxy destination and the hard loopback row. An unavailable enforcement tuple never activates it. The OS backend installs this fixed shell only after that gate is qualified; its non-login shell above remains the agent/service default. This project-side class does not change donor provisioning (§1.1).

### 4.4 `user.retire`

Figure [M-UM2: provision, retire and recovery](../diagrams/provision-retire-recovery.puml) shows forward recovery, the quiescence gate and egress cleanup last.

```
args:   { generation: "9ac67d3418e04b0aafe89c6d72b54103" }
result: { username, generation, state: "removed" }
```

1. Persist `retiring` (commit point). The launcher refuses new starts for the generation from now on.
2. Locally stop the account's per-user service domain where available, signal every process of the generation's UID with TERM, grace and KILL, and verify zero processes over a quiet period. This is the same termination scope as `exec.stop` (§4.7), with generation/OS identity checked before every action. `processes_remain`, failed, partial or unknown observations leave unfinished admitted work in `retiring`, never success.
3. (v1) Keep the account's egress denial in place throughout cleanup. A workspace-capable allocation carries the R-TRANSFER export cleanup obligation (§7): home deletion waits for recorded export or explicit operator waiver. Ordinary dispatcher retirement collects and durably records the result and every referenced blob outside the home and retirement deletion path before entering `retiring` (§7); a digest-only journal entry is insufficient. Bounded cleanup export after ordinary caller/allocation expiry requires explicit original-admission consent (§7), while the generation remains `active`; the launcher has no retirement bypass. Direct operator retirement is the explicit per-act export-obligation waiver, requiring authentication plus exact-content confirmation and journaling (for example after compromise). The dispatcher owns export; deterministic refusal, failed, partial or unknown evidence retains the obligation. Bounded repair is separately admitted forward work under current authority, never a cleanup-only continuation; standing discard remains off and unchosen.
4. Move the home into `quarantine/` on the same filesystem, destroy declared keys before the walk, then delete all home and required temporary-area objects through bounded, journaled descriptor-relative batches (§§4.4.1, 4.6, 6). Yield the shared lock between batches; unrelated safe operations need not wait for full traversal.
5. Only after verified full cleanup remove the account and group, then per-account firewall rules (the static range deny remains), and persist `removed`.

Retirement makes no call to the broker. Binding cleanup stays with the dispatcher or configured operator through the broker API, separate effect IDs, observations and tombstones. Ordinary dispatcher cleanup confirms unbind before retirement. A direct operator retirement works through broker outage, refusal or fenced restore; any unconfirmed unbind remains an explicit durable cleanup obligation at that dispatcher/operator boundary. A retirement result is neither an unbind receipt nor evidence that delivered tokens were erased. A recycled UID never inherits the old binding. Retirement is forward-only admitted work under R-OUTCOME (§4.6).

Account retirement does not revoke an agent identity. For a one-shot worker, the dispatcher performs identity revocation as a **separate operation after account retirement**, only for identities it registered with a recorded one-shot flag. For standing agents (including orchestrators and fixed team roles), retirement leaves the identity intact; only the operator may revoke it, with a signed record (D-IDENTITY). Binding cleanup, account removal and identity revocation are distinct operations.

#### 4.4.1 Retirement deletion and metadata export

Figure [M-UM3: receipt evidence and retirement fate](../diagrams/receipt-archive-states.puml) shows declared-key cleanup, home deletion and metadata retention. The accepted owner decision of 2026-10-12 makes home deletion the ordinary retirement path; `user.retire` has no archive/delete/keep selector.

- **Declared keys are destroyed before the walk.** After verified quiescence and quarantine, in bounded journaled steps under the shared lock (§4.6), the helper MUST destroy key material at every declared key path through trusted descriptors without following links, before the deletion walk. Recovery MUST establish successful destruction or confirmed prior absence before continuing. A failed or unknown destruction result leaves the generation `retiring`. The dispatcher defines the caller key's role and generation in dispatcher §§3.3, 5.2; trusted home-relative path declarations and their format remain unpublished (§14, question 6). No recursive search is a substitute for this prerequisite.
- **Export before deletion (R-TRANSFER).** The dispatcher records workspace export after account-wide confirmed absence and before retirement (§7). Discharge requires a journaled complete-content receipt: result and every referenced blob digest/size-verified and durable outside the child home and retirement deletion path, or an explicit operator waiver. Retained content survives home deletion until authenticated import acknowledgement or another explicit authorized release; retirement need not wait for import. The helper preserves the cleanup obligation on missing/corrupt blobs, storage failure, deterministic refusal or incomplete evidence; record/interlock and custody/release encoding would need joint publication (§14, question 15). Direct operator retirement is that explicit waiver, not a silent missing-export fallback. Workspace result data is separate from the service-generated retirement metadata below.
- **Delete the home.** The descriptor-relative walk deletes all home content, names and links in bounded serialized batches, unlinking links without following them (§6) and yielding the shared lock between batches (§4.6). Each batch revalidates protected state and quiescence/key-cleanup prerequisites; a batch result never stands for full deletion. Successful deletion or confirmed prior absence is required before retirement can reach `removed`. Failed, partial or unknown deletion keeps the generation `retiring` and recovery resumes forward; unreadability is never absence. There is no positive classification of arbitrary agent-owned material.
- **Only a service-generated metadata export remains.** The retirement export MUST use a closed schema with explicit service provenance checks. It MUST contain no agent-controlled strings, names, links or bodies; account names and labels from caller input are not exportable. It is generated from trusted service records, never by scanning or copying the home. The concrete schema, provenance checks and audit encoding are unpublished (§14, question 6), and export publication stays disabled until they are published and qualified. Unknown provenance or schema failure prevents export publication. Export absence does not excuse incomplete home deletion.
- Code and results follow R-TRANSFER (§7) and their separate confidentiality policy. Git acceptance does not establish that content is secret-free, and those artifacts and free-text logs do not inherit the metadata export's confidentiality claim.
- **Keeping a home is a separate explicit operator operation. Its confidentiality is not guaranteed.** It requires `swarma-operator` authentication plus confirmation of that act's exact content and is refused from inside an agent session (§3). This is not a `user.retire` option and grants no authority to a dispatcher or installer. Its signed operator record format and ordering against retirement would need publication (§14, questions 1, 17); until then it is not admitted. There is no automatic retention of an arbitrary home.
- The existing `archive/` directory and `archive.sweep` name now refer only to metadata exports. The directory remains root-owned mode 0700 and export files root-owned mode 0600. The existing `archive` configuration block retains its directory and `retention.max_age` / `retention.max_total` policy; the previous home default, tar format, exclusions and per-home archive bound are removed. The sweep removes metadata exports older than `max_age`, then the oldest until the total is under `max_total`, at every retirement and from a daily root timer. Sweep never removes ledger, effect or tombstone evidence whose retention obligation is still live (§4.6), and never retains or classifies a home. Concrete export naming and size limits would need publication (§14, question 6).
- The retirement audit MUST record verified quiescence, declared-key destruction, home/temporary-file deletion and metadata export outcomes, including failed or unknown results, without secret contents. These are audit requirements, not new wire members (§14, question 6).
- R-TIME: expiry-driven retirement/home deletion requires the dispatcher's watermarked wall-clock expiry check AND accumulated boot-inclusive monotonic elapsed time of at least the allocation lifetime from activation (dispatcher §§3.5, 7.2, 11). Linux `CLOCK_BOOTTIME` / macOS continuous time is accumulated durably within boot epochs; reboot downtime is not counted and can only delay destruction. A clock step alone cannot delete a home. The common time-confidence policy holds time-driven destruction/reclamation after clock anomalies or unconfirmed boot time; explicit stops and operator retirements remain available (§11). No helper time wire field is added.

### 4.5 `user.list` and the ledger

The ledger is a root-owned, world-readable file with one record per generation: `{ generation, username, uid, gid, kind, label, state, created_at, created_by, retired_at? }`. It contains no secrets. It is replaced atomically (temporary file, flush, rename, directory flush) in a root-owned directory. Other components (broker, launcher, dispatcher and session host) read it directly; `user.list` returns the same records. Readability is not authority. Neither an `active`/idle lifecycle label nor a missing receipt proves that a generation was never launched or is currently absent (§8.3). The ledger alone does not establish whether an effect was recorded: `effect.observe` consults the receiver-owned caller/effect journal mapping under the shared lock (§4.6), never infers absence from a missing reusable UID or label.

**Ledger store epoch (R-GEN).** The ledger carries a monotonic store epoch; each direct reader durably records its highest observed epoch in its own state and refuses a lower one until operator reconciliation. Epoch envelope/floor encoding is unpublished (§14, question 9), so the record sketch assigns no new member. A floor helps only if it survives outside the restored failure domain; it complements the external restore fence and coverage proof. Missing/invalid shared state closes admission, never an empty ledger. `user.list`, receipts and retained records support dispatcher reverse inventory; an orphan requires operator decision, never automatic adoption/deletion by name or UID.

### 4.6 Lock, journal and idempotency

Figure [M-UM2: provision, retire and recovery](../diagrams/provision-retire-recovery.puml) distinguishes creation rollback from retirement recovery and effect replay.

- One durable lock (an exclusive lock on a root-owned file) serialises protected ledger/journal/receipt/accounting transitions of both binaries, including recovery and allocation. It is retained for bounded root pre-exec exclusion through verified privilege drop (R-FD3), and yielded between retirement batches; it is not a lock around unbounded traversal.
- Every mutating operation writes caller/effect- and generation-scoped journal records of planned and completed steps before acting. Recovery runs by dependency before an operation: validate shared ledger/journal integrity, all UID reservations and quota accounting, then recover its prerequisites, comparing OS objects with the journal before every action. Interrupted creation rolls back; interrupted stop and retirement continue their admitted effects. A safely classified retirement of another generation need not finish before an unrelated authenticated stop, observation or launch. Shared corruption, unbounded identity uncertainty or incomplete accounting closes the shared path.
- `request_id` is scoped to the caller's principal. A terminal repeated mutating `(caller, request_id)` with the same operation and canonical arguments replays the recorded result together with the target's **current** state, so an old success never looks like a live account; unfinished admitted work continues under the same ID according to R-OUTCOME below; different arguments are refused (`request_id_conflict`).
- `effect.observe` reads the caller/effect mapping, canonical-argument digest, recorded result, rollback/removal evidence and current target state under the same lock as mutation and recovery. Observation is read-only: receiver-owned recovery may resolve existing journal work, but observation never creates, relaunches or stops a replacement effect. Missing, partial, failed or unreadable journal/target reads cannot establish `not_recorded`; incompatible evidence is `contradictory`, unavailable evidence is `unavailable`.
- Retain effect identity, canonical-argument digest, result/current-state linkage and rollback/removal tombstones for the full retry/reconciliation admission lifetime. Evidence may be discarded only when the corresponding original identities are permanently inadmissible. Expired or lost results/evidence yield `unavailable`, never `not_recorded`; neither a metadata sweep nor a ledger entry substitutes for that evidence. `not_recorded` requires complete authoritative coverage of the original caller/effect and its admission interval. The concrete retention bounds, permanent-inadmissibility rule and coverage proof would need publication before activation (§14, question 8); no retention duration or freshness field is invented here.
- A lost launch reply or failure after the root start receipt is resolved through the same effect ID and receipt. `recorded` includes the current execution evidence, not a readiness assertion. Unknown process/receipt outcomes retain the claim until reconciliation and never permit a second launch (§§4.7, 7).
- Every operation appends one line to a root-owned audit log: time, caller, operation, arguments, result.

**Bounded scheduling.** Each invocation admits only a finite recovery budget before the requested operation. Retirement uses a finite cleanup quantum bounded in entries, depth/traversal work and elapsed cooperative work; deletion batches are serialized and release the global lock between batches. Reacquisition revalidates generation, journal, protected descriptors, quiescence and key-destruction prerequisites. Pending retirement keeps UID/quota reservations, admission fence and evidence. Fair scheduling gives controls and pending cleanup progress through dispatcher cleanup/sweep retries or explicit operator resumption of the original effect. The metadata-only daily root timer gains no retirement authority. Numeric budgets, lock-wait/batch deadlines, fairness/resume mechanism and their encoding would need publication and platform qualification (§14, question 10); idempotent re-walking alone is not a progress proof. These bounds cover cooperative work on a functioning filesystem, not a stuck kernel/storage device.

**R-LOCK: never hold its state lock across a synchronous call to another platform service.** Retirement has no such call. If a qualified apply needs a proxy-service query, journal immutable intent and a per-record in-flight marker under the lock, release it for bounded I/O, then reacquire and validate generation, current fences/versions and listener evidence before commit. An in-flight generation cannot activate/launch; a late result cannot reopen cancelled/retiring authority. Stored verdicts are not authority caches. R-FD3 root generation exclusion is an ownership constraint and is not mechanically released by this rule.

| Wait/lock graph edge | Lock while waiting / dependency rule |
|---|---|
| Caller → helper/launcher | Caller releases its service state lock; receiver independently verifies authority |
| Helper/launcher → local journal, OS backend, file/firewall work | Shared lock for bounded transitions; dependency recovery and batch yielding |
| Launcher → FD3 staging / privilege drop | Bounded R-FD3 exclusion; no wait for an executor unable to start |
| Helper → proxy evidence query, if selected | No shared state lock; per-record in-flight marker, bounded call, revalidate on return |
| Helper → broker | No edge: binding cleanup belongs to dispatcher/operator |

The published wait/lock graph must stay acyclic; bounds and concurrency qualify before activation. No other synchronous platform-service wait is admitted under the shared lock.

#### 4.6.1 State loss and restore (R-GEN)

A declared restore or state loss is an operator incident, not ordinary journal crash recovery. Before restored bytes become visible, install a restore mark outside the restored domain and close **all** ledger consumers: broker, launcher, dispatcher and session host. Keep new dispatcher admission closed. A snapshot, same-domain audit or epoch counter cannot certify its own rollback.

Reconcile ledger/journal with surviving OS inventory, preserved receipts/audit, broker tombstones, dispatcher/host records and external operator evidence. A generation recorded as `retiring` or `removed` by surviving authoritative evidence never returns to `active`. An `active` ledger entry without an OS account is contradictory, not a creation to resume. Names/reusable UIDs establish neither adoption nor deletion authority. Preserve ambiguous process claims and orphan obligations; no live-supervisor adoption.

For pre-restore admission intervals, `effect.observe` returns `unavailable`, never `not_recorded`, until complete authoritative coverage is re-established. Conflicting authoritative evidence returns `contradictory`. Only explicit operator reconciliation of identities, accounting, surviving process/effect evidence and reader floors can release the external fence. If completeness cannot be established, remain closed; no bounded recovery is promised after evidence loss. An undeclared internally consistent whole-machine rollback cannot be detected locally. Restore mark/epoch encoding, coverage proof and operator release protocol would need publication (§14, question 9); the dispatcher owns its own reverse-inventory/restore procedure.

#### 4.6.2 Receiver outcome tables (R-OUTCOME)

These tables own create, launch, stop and retire outcomes using exactly the six R-OBS states. The v1/S2 contract package must add `fw.apply`/`fw.remove` outcome tables for the same six states; those tables and the per-account freeze lifecycle are not specified or activated by this revision (§14, questions 18, 21). Diagnostics need not be terminal results. Pre-admission rejection records no receiver intent (audit is separate); `not_recorded` needs complete authoritative coverage. Every retry creating authority passes fresh permission, expiry and revocation checks when applicable. A lost transport reply is caller-side unknown until receiver observation supplies one of these states; transport loss alone cannot assign a receiver state. Transport uncertainty is observed; it does not establish durable `pending` intent. An original principal whose mutation grant lapsed may continue its admitted narrowing stop, never create/bind/launch authority. Continuations preserve **all** canonical arguments, including `grace_seconds`; changes remain `request_id_conflict`.

**`user.create`**

| Outcome/evidence | R-OBS state | Replay or continuation |
|---|---|---|
| Rejection before intent, with complete coverage | `not_recorded` | Fresh admission; no automatic create |
| Durable creation intent; OS steps/rollback unfinished | `pending` | Receiver rolls back interrupted creation; no second account |
| Authoritative rollback evidence | `rolled_back` | Preserve tombstone; new create needs fresh authority |
| Terminal creation result | `recorded` | Result plus current generation/state; no resurrection |
| Missing/expired/failed receiver evidence or unavailable observation after transport loss | `unavailable` | Observe original effect; uncertainty alone proves no receiver state |
| Conflicting authoritative intent/OS/result evidence | `contradictory` | Hold and reconcile; no creation |

**`launch.start`**

| Outcome/evidence | R-OBS state | Replay or continuation |
|---|---|---|
| Rejection before intent, with complete coverage | `not_recorded` | Fresh admission, no cached authority |
| Durable intent; receipt/drop/exec unresolved | `pending` | Reconcile same effect/receipt; never another physical start |
| Authoritative rollback and confirmed no surviving process | `rolled_back` | Preserve evidence; replacement needs fresh claim/admission |
| Terminal launch result, including terminal failure | `recorded` | Result plus current execution/account evidence; not readiness |
| Missing/expired/failed receiver evidence or unavailable observation after transport loss | `unavailable` | Retain claim; observe original effect; never infer absence |
| Conflicting authoritative receipt/process/journal evidence | `contradictory` | Fence and reconcile; no second start |

**`exec.stop`**

| Outcome/evidence | R-OBS state | Replay or continuation |
|---|---|---|
| Rejection before intent, with complete coverage | `not_recorded` | Fresh admission; current execution/identity checks remain |
| Admitted intent; `processes_remain` or unresolved process observation | `pending` | Same effect/arguments; recheck generation/latest receipt every time |
| Authoritative rollback before any stop action only | `rolled_back` | No rollback once termination actions began; purported reversal is contradictory, not renewed authority |
| Confirmed absence / terminal non-signalling refusal | `recorded` | Replay result/current state; completed stop never signals again |
| Missing/expired/failed receiver evidence or unavailable observation after transport loss | `unavailable` | Observe original effect; no invented stop receipt |
| Conflicting authoritative receipt/process/journal evidence | `contradictory` | No unsafe signalling; hold for reconciliation |

**`user.retire`**

| Outcome/evidence | R-OBS state | Replay or continuation |
|---|---|---|
| Rejection before retiring intent, with complete coverage | `not_recorded` | Fresh admission; no implied deletion |
| Admitted retiring intent; failed/unknown forward step or remaining batches | `pending` | Same-effect forward recovery; retain reservation/fence/evidence |
| Authoritative rollback before retiring commit only | `rolled_back` | Never roll `retiring` back to `active`; preserve evidence |
| Terminal removal after all prerequisites | `recorded` | Replay/current state; not broker unbind evidence |
| Missing/expired/failed receiver evidence or unavailable observation after transport loss | `unavailable` | Observe original effect; never infer deletion/absence |
| Conflicting authoritative lifecycle/OS/journal evidence | `contradictory` | Hold and reconcile; no restored active authority |

Unfinished admitted work maps to dispatcher pending handling, never terminal `refused`. Broker bind/unbind tables belong to that receiver; dispatcher §§4.5–4.6, 7.1 reference these tables. Exact result/observation encodings remain unpublished (§14, question 8); no seventh state or refusal code is added.

### 4.7 `exec.stop`

Figures [M-UM2: launch and authorised stop](../diagrams/launch.puml) and [M-UM3: receipt evidence and retirement fate](../diagrams/receipt-archive-states.puml) distinguish a start receipt from confirmed process absence.

```
args:   { generation: "9ac67d3418e04b0aafe89c6d72b54103", execution_id: "EX-…", grace_seconds: 10 }
result: { execution_id, stopped_at, receipt: { signalled, killed, remaining: 0 } }
```

Ordinary `exec.stop` is allowed to the dispatcher for generations it created; the caller stays the dispatcher under R-SESSION. Under an authenticated R-ALLSTOP operator act, the configured operator helper path may initiate the receipt-backed generation stop independently of dispatcher availability (§§2–3, 8.3), with the helper journaling its receiver part. That exception confers no ordinary stop or launcher authority. The current terminal transition applies; the phone-to-helper transition remains gated (§14, question 17). The ordinary argument sketch above is not an encoding of the unpublished operator act. Never-launched generations use §8.3's fenced absence outcome instead of `exec.stop`; missing receipts alone cannot select it. Only the configured session-host principal requests `host_stop` through `dispatch-op/1` only for an execution under its session-scoped host admission permit. The dispatcher journals E-stop, invokes `exec.stop` and confirms absence; it records host-requested stop separately from owner `cancel`. `host_stop` confers no start authority (§7).

Under the shared lock, validate shared identity/accounting and recover operation dependencies. Replay an already terminal stop result without signalling before testing the current live-execution fence. For unfinished or new stop work, check the active generation, dispatcher ownership or admitted R-ALLSTOP operator authority, and root-owned start receipt (§7). The requested `execution_id` MUST be the generation's latest receipt before signalling and on every continuation. The receipt's `pid`, `start_time`, `boot_id`, `session_id` and generation authenticate the target execution; match any live receipt target against these identities and the UID, refusing reused identity. If that root is already absent, authoritative receipt/current-generation evidence is still required to address escaped children; a failed identity read is not root absence. Receipt values do **not** bound termination by session or wall-clock start time.

While one execution per generation holds, stop and retirement use one scope: stop the per-user service domain where available; TERM every process of the generation's UID, wait the original bounded grace period, KILL remaining members, and verify zero account processes over a quiet period, including `setsid`, double-fork, pre-receipt and OS-spawned processes. Re-enumerate/revalidate process identities and the generation fence before signalling; UID reuse is never authority. The selected root-created non-delegated Linux per-execution unit assists containment (R-CEILINGS), but account-wide absence stays decisive (§7). R-WATCH requests a journaled dispatcher `exec.stop` for one account; R-ALLSTOP uses this scope for receipt-backed generations and the separate never-launched inventory case in §8.3, retaining unresolved evidence and closed admission on partial or unknown results. An old receipt cannot stop a later sequential execution. Future concurrent executions per generation require exact per-execution containment; session-only termination is never a substitute.

Return the stop receipt only after verified zero processes. `processes_remain` and failed/partial/unknown observations leave admitted work `pending`, not a terminal replayed failure (R-OUTCOME). Continue under the same effect ID and exact canonical arguments, including `grace_seconds`; revalidate the latest-receipt fence each time. A later receipt refuses old-stop signalling. Once absence is terminally recorded, replay returns recorded result/current state **without signalling**, even after a successor launch. Quiet-period/local wait bounds would need publication and qualification (§14, question 10); unkillable processes stay unresolved. sudo is the invocation boundary, never a signal relay.

Each materialize, work and export execution has its own latest root receipt and claim (§§5, 7). Confirm account-wide absence for each before admitting the next; ambiguous launch/stop evidence is reconciled under its original effect, never relabelled as export evidence. Workplace tool-write and SSH-ingress fences remain closed from round quiescence through export, reopening only for a separately admitted repair turn (§7). These fences do not make a failed process scan evidence of absence.

`exec.stop` proves **process absence only**. It is harness-agnostic and MUST NOT attest that a harness's native session lock is absent. Before reopening or resuming, session-host recovery (session-host §3.5) requires a freshly launched runner under the agent account to check the native lock under a closed fence and report the result to the host; an unknown result keeps the session parked. A stop receipt never substitutes for that check (R2).

## 5. Cross-component reconciliation

The dispatcher caller's `request_id` correlates one caller-scoped dispatcher request. It is distinct from each downstream effect's idempotency key. The dispatcher derives a separate effect ID for every create, bind, launch, stop, unbind and retire operation: the first 32 hexadecimal characters of SHA-256 over `swarma-dispatcher effect/1` plus CCJ-1 `{caller principal, request_id, record id, component, operation, attempt}` (dispatcher §4.5; no newline is added to this formula).

| Effect | Receiver | Received `request_id` |
|---|---|---|
| `user.create` | Helper | Create effect ID |
| `bind` | Broker | Bind effect ID |
| `launch.start` | Launcher | Launch effect ID |
| `exec.stop` | Helper | Stop effect ID |
| `unbind` | Broker | Unbind effect ID |
| `user.retire` | Helper | Retire effect ID |

Materialize, work and export each use distinct existing execution records, claims, launch/stop effect IDs and root receipts, linked durably to the immutable round and export obligation (§7). The result's `execution_id` identifies the work being exported, not the exporter's physical start. Export collection has its own effect identity; a lost reply is observed/reconciled through its original evidence, never permission for another launch. Terminal export effects retain and replay their result; re-observation, repair and re-export use new linked effects and executions. No new operation name or receipt type is assigned.

Retries of the same effect reuse its ID; different operations MUST NOT reuse one ID. After a failure between components, the dispatcher observes the original effect IDs at their receivers before acting. Completed mutation replay still returns its recorded result under the receiver idempotency contract; authorised same-effect retries preserve the ID and canonical arguments. Observation alone never authorises a new create or replacement execution. The helper also returns the target's current state (§4.6). R-OUTCOME pending is unfinished admitted effect handling, never terminal refusal; it can still mean unknown target/process liveness. For R-OBS, the dispatcher maps `recorded` to present or absent according to the current target state; `rolled_back` and `not_recorded` to known absent for that effect only (never permission for an automatic new create); `pending` and `unavailable` to unknown; and `contradictory` to contradictory. Broker bind/unbind observation and removal/tombstone retention belong to the broker's `effect.observe` contract, not the helper ledger.

Root correlation stays in the dispatcher's effect table, not in an invented extra member of the closed helper/launcher schemas.

| Identifier | Meaning |
|---|---|
| Account `generation` | Fresh random 128-bit account instance (R-GEN); distinguishes UID reuse |
| Dispatcher `agent_id` | Allocation record |
| Dispatcher `run_id` | Execution record |
| `execution_id` | Execution claim and start-receipt identity |
| Launch `epoch` | Execution/launch fencing value; not the account generation or a session controller epoch |
| Broker `binding_id` | Never-reused broker binding identity |
| Broker `launch_id` | Correlation only (plan digest or run ID), never authority |
| Board run/attempt IDs | Separate optional client handles, not dispatcher execution IDs |

The contract does not freeze a `run_id` to `execution_id` construction; integrations preserve their distinct roles rather than inventing an equality.

## 6. File operations

Figure [M-UM4: storage layout and owners](../diagrams/storage-layout.puml) maps the protected paths and no-follow boundary.

- Control paths (configuration, ledger, journal, audit, quarantine, archive, the homes' roots) are root-owned directories that are not writable by others; a control path that is a symbolic link refuses (`path_is_link`).
- All operations work relative to trusted directory descriptors and never follow links: on Linux through `openat2` with `RESOLVE_BENEATH` and `RESOLVE_NO_SYMLINKS`; on macOS through a per-component `openat` walk with `O_NOFOLLOW` (`O_NOFOLLOW_ANY` where available). Every opened object is checked with `fstat` for type, owner and device where it matters.
- Homes are created with `mkdirat`, `fchown` and `fchmod` on the descriptor. The helper never runs a recursive `chown` over content an agent controls.
- Inside a home, symbolic links are ordinary objects: deletion unlinks them without following them (§4.4.1). Metadata export never copies home links. A home therefore never becomes unremovable because it contains links.
- Bounded deletion batches yield the shared lock (§4.6), revalidate protected state/descriptors and prerequisites on reacquisition, and retain reservations/evidence until full cleanup. Safe re-walking must establish finite work and forward progress for deep/wide trees; no agent-supplied continuation is authoritative. Temporary-area and UID-hygiene walks also require explicit bounded work; failed reads never establish clean/absent.
- Destructive walks start only after the account is quiescent (§4.4) and the home has been moved into quarantine, so no process of the account can swap a directory during the walk.

## 7. The launcher (`swarma-user-launcher`)

Figure [M-UM2: launch and authorised stop](../diagrams/launch.puml) shows the root receipt write before privilege drop, refusal branches and authorised stop. [M-UM1: privileged components](../diagrams/components.puml) shows the launcher as a separate process.

Shared-rule names in this section refer to the typed owner-linked index through §14; historical audit labels supply no rule or intake authority.

The launcher starts one approved executor under one active agent or qualified workplace generation. Workplace jobs use the same receipt/stop path only after joint backend publication (§14, question 11); service-side `swarma-rb-exec` never runs under the workplace UID.

**Only the dispatcher invokes the launcher (R-START).** A session host asks the dispatcher through `host_start` in `dispatch-op/1`; it never invokes either privileged binary. The dispatcher owns the durable **host admission permit**, session-scoped for one `logical_session_id` (R-SESSION). The owner's admitted start may explicitly authorise successors through **session lifecycle authorisation**, whose member format is unpublished. Every physical start keeps its own `(execution_id, controller_epoch, op_id)` claim, fence and receipt interlock. A successor `host_start` is admissible only under that authorisation, is idempotent per `(logical_session_id, op_id)`, and requires the previous claim confirmed absent first. The dispatcher uses its existing effect/root-receipt path for the approved agent-side runner. Its R-SESSION admission keeps the same allocation/generation and stored plan verbatim, current owner authority, grant window and allocation lifetime, with fresh `revocation.check` context `start` on each use (dispatcher §12); a one-start request without lifecycle authorisation admits no successor. The host acquires no caller chain or plan-authoring authority. A fence change withdraws the permit or sends it to reconciliation. Cancellation before the call prevents it; an ambiguous call is resolved through the same effect and receipt, with a stop if required and no second launch. The runner opens a fresh authenticated channel to the host; current-epoch registration and readiness precede delivery. Host failure keeps the claim and delivery fence closed until reconciliation. Controller-only re-adoption preserves the execution ID; actual replacement uses a new one. The joint I4 contract for host authentication, durable permit/fence/crash ordering and readiness would need publication and qualification (§14, question 3); SH2+ activation remains gated. These dispatcher/session-host values add no members to `launch-op/1`. There is no helper host role, host sudo authority, launch ticket or redemption journal.

```
swarma-user-manager launch-op/1
{ v: 1,
  op:         "launch.start",
  request_id: string (≤ 64),                 // launch effect idempotency key, §5
  generation:   "9ac67d3418e04b0aafe89c6d72b54103",
  execution_id: "EX-…",                      // from the dispatcher's execution claim
  epoch:        3,
  executor:     "curator-run",     // an id from the approved list
  plan:         base64 (encoded ≤ 64 KiB; decoded ≤ 48 KiB) }  // delivered on descriptor 3; request ≤ 80 KiB
```

This section owns the single launcher descriptor-lifecycle contract (R-FD3); the agent launcher's §10.1 references it. The required order is:

1. Scrub all untrusted inherited descriptors above caller-owned 0–2 **before** creating trusted internal handles. No service or broker connection is inherited. Reserve read-only FD3 for the plan without clobbering any internal lock, executable or directory handle.
2. Acquire the shared generation lock (§4.6), validate shared integrity/reservations/accounting, recover only dependencies within the published budget and read the ledger: the generation is `active`, of kind agent (or workplace only after its qualification gate), and created by the calling dispatcher (`generation_not_active`, `target_not_owned`). Before a new physical start, refuse while the root-owned R-ALLSTOP mark is set (§8.3), including a request issued before the act and every approved workspace executor. Under the same lock, verify the pinned exec-profile identity and resolved policy-body digest from the protected machine relation (§8); drift refuses without substitution. Retry/recovery use that same pin. Verify the recorded admission class against the published host capability matrix, the task exec profile, network/socket and deployment gates (§§3, 7–8, 12); missing or unknown evidence refuses. Apply the qualified per-execution containment and restrictions selected by R-CEILINGS/R-EXEC/R-NET-TOOL before any child code starts. Establish zero account processes and no unresolved prior execution/stop claim; a failed/partial scan keeps launch closed. Keep this lock through the root receipt and the **completed, verified UID/GID transition** in step 7. Retirement and stop cannot interleave while the launcher is still root.
3. Resolve `executor` in the root-owned approved list to an absolute path in a root-owned directory and a SHA-256 digest; open it without following links and verify the digest (`executor_not_approved`, `executable_digest_mismatch`). Keep the verified executable handle until the kernel exec operation; initial descriptor scrubbing must not close it. Open the agent home without following links and use it as cwd; the executor later prepares `work/` and `tmp/` under the agent UID. Close the directory handle after its last use.
4. Completely stage the admitted decoded plan as **bounded, immutable bytes on read-only FD3**, preserving the admitted digest and the 48 KiB decoded / 80 KiB request bounds (§2). The plan must be fully readable before the executor starts and immutable to the agent. Staging and the entire pre-exec path MUST be bounded, including interrupted staging and cleanup while the generation lock is held. The per-platform mechanism and bounds would need publication (§14, question 7). A pipe is allowed only with a published and qualified capacity/feeder/deadline/cleanup order that never waits for a reader unable to start; writing the maximum plan into an unqualified pipe before exec is not an admitted mechanism. There is no path/stdin/network fallback or arbitrary caller argv.
5. Build the environment from a fixed set (`HOME`, `USER`, `LOGNAME`, `PATH`, `LANG`, `TMPDIR` inside the home); nothing is inherited. Standard input, output and error remain the caller's pipes or terminal.
6. Refuse if a start receipt for this `execution_id` already exists (`execution_already_started`); otherwise start a new session (`setsid`) and, **while still root and holding the generation lock**, write the atomic root-owned **start receipt** `lib/user-manager/receipts/<generation>/<execution_id>.json` (`{ execution_id, epoch, pid, start_time, boot_id, session_id }`, mode 0644). Close receipt/journal handles at their last use without releasing generation exclusion early.
7. Set supplementary groups to none, then the GID, then the UID (real, effective and saved), and verify that root cannot be regained (`privilege_drop_failed`). Only once the transition has completed and this process is the receipt-matching agent execution may the launcher release and close the generation lock. Failure after receipt persistence retains that evidence for same-effect reconciliation, even if exec never occurs.
8. Exec the verified executable (Linux by the retained descriptor with `execveat`; macOS by its path in the protected root-owned directory). Retain the verified handle through exec; internal handles close at their last safe use or through platform-qualified close-on-exec. The executor receives **only 0–2 and read-only FD3**, with no lock, verified-executable, directory, receipt, journal, service, broker or root handle. On every failure, including staging, receipt/drop and exec failure, release all internal handles and staging resources while preserving durable effect/receipt evidence; a failed or unknown cleanup/process observation never proves absence or authorises another start. The concrete exec/close-on-exec behavior is part of the platform qualification gate (§§12, 14).

Executor activation requires joint publication and platform qualification of the selected FD3 mechanism and every R-FD3 row in §12.

**Process fate table (R-FATE).** This section owns the table next to R-FD3; dispatcher, session host and broker reference it. Service-manager defaults, ancestry, UID change and `setsid` do not define containment. Platform services and service managers end executions only through journaled `exec.stop`, retirement or operator emergency stop. OS faults such as OOM remain possible and are recorded as `lost`, never confirmed stop receipts.

| Process class | Required unit/kill domain and survival | Stop, crash and restart/replacement of services | Death evidence and maintenance affected set (R-MAINT) |
|---|---|---|---|
| Dispatcher daemon | Protected dispatcher service unit; no implicit execution kill by defaults | Dispatcher stop/crash/restart replaces its instance; broker/host loss alone does not kill it | Service identity/death evidence; dispatcher swap includes all supervisor-backend executions and every other execution whose published containment/dependency is affected |
| Dispatcher supervisor | Dispatcher-instance ownership domain; no live adoption | Dispatcher loss/replacement fences all old writers; supervisor-backend executions take `lost`, then journaled stop. Broker/host loss is reconciled without automatic starts | Durable daemon-instance epoch checked on every record write; old-instance survivors cannot write. Absence of every affected execution precedes swap |
| Execution root (`curator-run`, SH2+ runner or approved workspace executor) and descendants | Linux: selected root-created non-delegated per-execution unit; macOS: qualified R-CEILINGS mechanisms, separated from unrelated service kill domains; one execution per generation | Supervisor backend promises no survival on dispatcher loss. SH2+ runner backend promises survival across controller-only dispatcher/host restart only with qualified containment; controller-only re-adoption preserves execution ID. Broker loss alone does not terminate it; credential/delivery failures close relevant fences | Journaled stop/retirement with account-wide absence, or `lost` on unexpected/OS death. Every supervisor write rejects a stale durable daemon-instance epoch, even if the writer survives a replaced daemon. Late completions may resolve historical evidence under current fences but never reopen admission/delivery or resurrect cancelled starts (R-LOCK). No live-supervisor adoption.

**Resource ceilings (R-CEILINGS).** For agent and workplace executions on Linux, the root-created, non-delegated per-execution unit outside the dispatcher unit is selected, created through systemd where it owns the tree. It applies CPU, memory, task and IO limits; a private temporary directory, no new privileges and a read-only system; a per-UID disk quota on the agents filesystem; `KillUserProcesses=yes` and `/proc` with `hidepid=2`; the R-EXEC allowlist, the R-NET-TOOL network namespace and address-family restrictions; and a CPU-time budget per execution. An agent-writable delegated tree is not containment. Trusted model-provider access retains only the bound proxy path; the no-external-interface / Unix-only form is mandatory for workplaces (§8).

macOS uses a sandbox profile for exec, files and network; a per-user process-count limit and per-process CPU limits; the background scheduling class for agent processes (CPU and IO throttling); an APFS volume quota for the agents root (aggregate, not per account); and the watcher for memory and per-account disk (soft). A new session is identity evidence only; UID-wide absence remains decisive. Known qualification gaps are no public hard per-account memory ceiling, no per-user disk quota on APFS and a deprecated, though widely used, sandbox profile interface. These are soft or absent matrix rows, never an OS-name exclusion.

Each host publishes a qualified capability matrix per OS release as a qualification output (§12). For CPU, memory, process count, IO, disk, temporary areas, process visibility and network it records kernel-enforced (hard), watcher-enforced (soft) or absent. Admission classes declare minimums, and the dispatcher admits only when the matrix meets them. Untrusted-class minimums are a hard process-count ceiling, enforced zero or provider-only egress, an exec profile, isolated temporary areas and hard memory, CPU and disk ceilings where the host provides them. Whether soft rows are acceptable on a host lacking hard ones is an open owner decision, recorded per host by an operator act; no default acceptance is implied (§14, question 13).

Linux hosts admitting the untrusted class require the kernel baseline: unprivileged user namespaces, io_uring and unprivileged eBPF disabled; `kernel.yama.ptrace_scope=2`; and timely sudo patching. Host infrastructure installs it; the platform verifies it (§12). Concrete unit names/configurations, limits, membership/receipt association, daemon-epoch encoding and every fate/affected-set row would need publication and qualification (§14, question 13); deployments unable to honor promised survival remain gated. Defaults never supply missing evidence.

Ordinary execution lifetime belongs to the dispatcher and its journaled `exec.stop` path (§4.7). R-ALLSTOP adds the operator-initiated receiver stop/absence path when the dispatcher is unavailable (§8.3); the dispatcher later reconciles it without relaunch. sudo may or may not remain a parent, depending on its policy, and is never relied on to relay signals (it cannot forward SIGKILL). The harness executor is trusted platform code: for an admitted trusted agent it reads the plan, resolves the protected credential binding, obtains its lease from the broker on a fresh connection and execs the harness (broker §12.2). Workspace executors obtain no subscription lease and start no harness. Arbitrary `sudo -u` or a general command runner is never a substitute for the launcher.

D-EXECUTOR authorises a versioned, narrow agent-account one-shot mode for `curator-run`: it only verifies and executes an immutable plan composed on the caller's side, never composes or resolves profiles under the agent account, and reaches only its declared platform Unix sockets and the bound model-provider proxy; it has no general internet access (R-NET-TOOL). It shares a launch library with `swarma-session-runner`; a separate minimal executor binary remains a later option. `curator-run` under the agent account is the first broker consumer. The board runner and session host ask the dispatcher to launch through it; they do not embed broker clients. The executor's versioned intake and Decision 0021 amendment remain publication work owned by the [launcher intake lane, curator-agent-launcher SPEC §10](https://github.com/relux-works/curator-agent-launcher/blob/main/SPEC.md) and [Decision 0021](https://github.com/relux-works/curator-spec/blob/main/decisions/0021-sessions-enter-through-curator-run.md); this helper's FD3 transport does not claim that amendment is implemented.

The caller-composed plan records the resolved PATH and covers it with the plan digest (D-PATH): (1) this launch's protected tool directory (CIP-0007), (2) the user's admitted base PATH in its existing order, (3) one protected manager dispatcher directory, through which project commands run only after checks. The executor verifies and uses that plan; a repository `.agents/bin` is never executed in a managed launch. This launch PATH is distinct from the launcher's fixed bootstrap environment in step 5.

**Exec profile (R-EXEC).** Every agent or workplace task class has an executable allowlist enforced by the OS, never by PATH alone: on Linux the per-execution unit makes all paths non-executable except the allowlist; on macOS a sandbox restricts process execution to the allowlist. Writable areas are never executable. The account's task tools exclude compilers, linkers, transpilers, bundlers, test runners, package managers/installers, container/VM tools, network tools, and harness/agent binaries. No account may start its own agent loop or agent environment: only the executor path of the admitted plan starts the harness. Editing, version-control inspection, search and qualified light checks such as type checking may be allowed per profile. Interpreters require an explicit protected profile entry and full invocation qualification below; ceilings remain the resource bound, never proof of inert input. Where one executable serves light and heavy actions, only the protected wrapper in the manager dispatcher directory (D-PATH) may invoke it, with a fixed subcommand allowlist; qualification proves the heavy form refuses and the underlying executable cannot be reached directly or indirectly; root ownership of a wrapper alone is insufficient. The dispatcher job class `agent-headless-build` is withdrawn for agent accounts.

**Complete invocation qualification (R-EXEC).** A locally admitted tool must establish the boundary for its executable, fixed entrypoint and arguments, constrained environment, and every transitive input it can interpret as code or configuration. Inert inspection of candidate bytes is distinct from executing candidate-supplied inline evaluation, readable scripts, module imports, plugins, startup files or executable project configuration. An executable allowlist, non-executable writable area, fixed subcommand or resource ceiling does not establish inertness. Use protected fixed entrypoints/configuration and disabled or pinned code-loading mechanisms where supported; worker-controlled inputs must not select or supply executable behavior. Qualification drives the actual task-tool path, including indirect shared-tool invocation, with negative cases and positive inert-light-check controls (§12). If a tool/release cannot establish this boundary, refuse that local profile and route the operation to R-VERIFY. No new privileged wrapper service is selected.

**Verification (R-VERIFY).** Compilation, transpilation, builds, test suites, generators and any execution of worker-produced code run only through controlled verification in isolated ephemeral runners on another machine, without secrets and with controlled dependency egress (§8). Results return as data to the board in the testing state. A tester agent orchestrates and reads results; it never executes the code itself. Dependencies for light checks come only from platform-seeded read-only caches; no download occurs inside an account. The runner pool, job contract and result format are unpublished and belong to the board/infrastructure lanes (§14, question 19).

**Standing placements (R-STANDING).** Standing sessions with a local agent loop admit trusted-class identities only. Untrusted long-lived placements are standing workplaces: their loop runs at the donor, no local agent environment starts, and no harness binary is executable from the workplace. Task OS services are whitelisted. Trusted standing harness settings, hooks, MCP configuration and instruction files come from the plan. The executor verifies their digests before every launch, restart and native resume, or supplies them from a root-owned location outside the home. Drift refuses launch and is reported; the refusal code is unpublished. Repair is explicit re-materialization, never silent acceptance (§14, question 20).

**Workspace administration and transfer (R-TRANSFER).** A child in another isolated account gets a standalone repository in its private home, with private `.git`, common directory, refs, index and freshly written local configuration: no hooks, remotes or credential helpers. No linked `git worktree` crosses that boundary. Copy/reflink optimization cannot share writable administration or mutable hard-linked metadata. Same-account worktrees and today's board workflow stay. The launcher still has no general workspace-copy operation. Materialization and export belong to the dispatcher's workspace contract; the board accepts the result only as a resource. Approved executors have the design labels `swarma-workspace-materialize` and `swarma-workspace-export`; each runs under the child UID with a fixed environment through the admitted launcher path. Export has no network. They are design labels, not new wire operations.

1. **Materialize before work.** The caller supplies exact admitted base B, a commit of its repository, as a bounded canonical archive of B's tree with the start request. The dispatcher relays it and journals its digest; it holds no repository. `swarma-workspace-materialize` writes the private standalone repository before work. The plan records B, the digest of B's canonical manifest (path to supported Git kind/mode and content identity), task write scope and exec profile; the plan digest covers them. Derive the manifest from B's immutable repository objects, never a working checkout; a symlink blob identifies its link-text bytes. Before work, the materializer verifies every archive entry's path, kind/mode and content identity against that manifest and refuses mismatches, missing or extra entries. The exporter retains immutable access to the same admitted manifest outside worker-controlled Git administration. The plan digest also pins the approved exporter digest, export cap values and a per-round bounded repair budget; their encoding and values remain unpublished. Task-resource digests are also in the plan; the platform materializes those resources read-only next to the workspace as data, never instructions (R-NET-TOOL 4a, §8). Tests/validators stay outside the write scope unless the task concerns them. Archive format and exact plan fields are unpublished (§14, question 15).
2. **Work and round end.** The worker has no network, push or merge-request access; its `.git`, commits and history are never consumed by the platform. Done is reported as a board outcome for a local agent or signed final envelope for a remote worker. The platform confirms no account process remains using §4.7. A workplace round is write-fenced: the project-side executor refuses further tool calls into it and SSH ingress is fenced from quiescence through export; both reopen only for a separately admitted repair turn. An intermediate export may be requested at a turn boundary under the same fence.
3. **Export after confirmed absence.** `swarma-workspace-export` walks without following links, skips every `.git` component and compares both kind/mode and content identity with the immutable admitted manifest. It emits only added/modified regular files (content and executable bit), symlinks as link text and deleted paths. Mode-only edits and equal-blob regular↔symlink transitions are `modify`; deletions carry the prior manifest mode. File count, per-file and total bytes are capped; binary files have a separate cap. The plan pins the exporter digest and caps; stop the walk at the first cap excess, never continue an unbounded walk. Special files, any `.git` component however spelled, case-fold or Unicode-normalisation collisions, gitlinks/submodules, root-escaping paths and exceeded caps refuse the whole export, with no partial result. The dispatcher journals a complete-content receipt only after the result and every referenced blob are digest/size-verified and durable in an admitted destination outside the child home and retirement deletion path. Protected storage or authenticated durable handoff may provide that custody; no new service/transport is mandated. Digest-only records, missing/corrupt blobs, storage failure or incomplete crash evidence keep the obligation pending and authorize no truncation. Result retrieval is separately authenticated to the original caller principal/requester under current release authority; cleanup consent or an archived signature never releases data to a revoked requester. Retain complete content with bounded storage accounting until authenticated import acknowledgement or another explicit authorized release; silent pre-import expiry is not successful delivery. An unavailable caller can require an explicit disposition. Home retirement need not wait for import once complete content survives independently. The result kind is the design label `swarma-dispatcher workspace-result/1`; the [dispatcher Revision 0.11 §5.2.1 DRAFT schema](https://github.com/relux-works/swarma-dispatcher/blob/74687e600e04817fa6e7a2e8904a9f7a3c83a1d8/spec/dispatcher.md#521-draft-swarma-dispatcher-workspace-result1) owns its exact fields. Draft result bytes do not publish transport, retention or the complete transfer lifecycle; those prerequisites remain gated through the owner references in §14. Export precedes retirement: a workspace-capable allocation carries an export cleanup obligation, and home deletion waits for recorded export or an operator act waiving it (§4.4). Direct operator retirement is that explicit waiver.
   **Cleanup admission and evidence.** Original workspace admission explicitly consents to bounded continuation of its durable export obligation after ordinary caller or allocation expiry, bound to the exact generation, round, approved exporter and immutable base/manifest/write scope. It authorizes collection only: no harness, subscription lease, network, new task, ordinary successor or worker repair. Every physical materialize/work/export launch has its own execution claim, E-launch/E-stop, root receipt and confirmed absence, linked to the round/obligation (§§4.7, 5). A lost reply never permits duplicate launch; reconcile the original effect/receipt. Cleanup runs only while the generation is `active`, never after `retiring`, never by a fabricated receipt or reused R-SESSION permit. Explicit revocation, compromise, R-ALLSTOP, maintenance and restore are separate security-hold cases, never implicitly bypassed by retention or expiry consent. Without valid cleanup authority keep the obligation held for an explicit operator export/recovery or per-act waiver decision; any admitted export still uses the dispatcher/launcher boundary. Reserve or retain bounded cleanup capacity with progress alongside forward work, preserving actual resource/storage safety, claim accounting and all security fences. Consent/hold semantics, scheduling and interlocks remain joint publication/qualification gates (§14, question 15).

   **Export outcomes and disposition.** Keep four classes distinct: recorded export with complete-content custody discharges; deterministic whole-export policy refusal retains; interrupted or unknown export (crash, OOM, I/O failure or deadline before verdict) stays pending/unresolved under the same effect and identical canonical arguments; authorized discard requires the explicit per-act operator waiver. These are export dispositions, not additional R-OBS states or wire values. Each completed effect replays its immutable terminal result; re-observation never reruns it or replaces its receipt, but uses a new linked effect. Over the same quiesced tree, conflicting recorded/refused outcome classes or recorded change-set digests are `contradictory`; refusal diagnostics are not compared because walk order is unpublished. No partial result is success and a refusal never becomes discharge by retry.

   **Unreadable source entries.** The approved exporter's own failed open/stat of a required source entry in its fixed, admitted and qualified reader environment must have a bounded repair/disposition path as a policy refusal or typed exporter failure; its class/encoding is unpublished, with no extension of the result schema here. Report only the known blocked entry or ancestor through the existing diagnostic contract. Source permission denial is distinct from infrastructure/admission denial (misapplied sandbox or inaccessible trusted manifest), EIO, unavailable storage, vanished volume and ambiguous identity; these remain pending/unresolved, never this source-entry refusal. Not every EACCES/EPERM proves source denial. Never chmod, mutate the tree or elevate exporter privilege. Classification alone never discharges or authorizes deletion. Qualification must use the actual admitted worker tools and approved exporter environment, not infer permission-changing capability from UID ownership (§12).

   **Bounded same-workspace repair.** The original caller may request a separately admitted continuation under valid current work authority, within the plan's per-round repair budget. Repair is a new fenced round on the same workspace, preserving valid edits rather than re-materializing. Give only refusal class and the known offending path to caller/worker through a task snapshot or letter, never a partial change set. Each repair turn and re-export uses new linked execution/effect identities; the refused result stays immutable. Reopen tool-write/SSH-ingress fences only for that admitted turn, then fence again, confirm account-wide absence and perform a new complete export. Cleanup-only authority after expiry cannot admit repair; R-ALLSTOP, restore and other security holds stay closed. Budget exhaustion retains the obligation; absent renewed valid work authority, the per-act operator waiver is the only discard path. Nothing is discarded automatically. Standing discard is optional owner policy, off and unchosen. Retention holds the home, account, UID reservation and live-allocation quota; execution capacity is released after confirmed absence. Repeated refusal can still require operator presence once per retained round.

4. **Candidate and review (board ownership).** The orchestrator runs the board's deterministic import (command unpublished), building on B in a scratch index with hooks disabled and no attribute filters/drivers. Independently recompute the canonical manifest from the caller repository's immutable B using the same canonical encoding as the admitted manifest, never the orchestrator-composed plan as the anchor. This is a bounded tree pass; refuse unless the recomputed digest equals the result's `manifest_digest` and `base_commit` equals B, preserving existing result-to-admission checks. It hard-refuses `.git` components, paths outside write scope and every change under `.task-board/`. CI (`.github/**`, `.gitlab-ci.yml`, `.circleci/**`), git behaviour (`.gitattributes`, `.gitmodules`), hooks/auto-run (`.githooks/**`, `.husky/**`, `.pre-commit-config.yaml`, `lefthook.yml`, `.envrc`, `.vscode/**`), agent instructions/config (`AGENTS.md` and `CLAUDE.md` in any directory, `.claude/**`, `.codex/**`, `.agents/**`, `.mcp.json`) and every symlink are flagged for explicit hunk-by-hunk review acknowledgement. Candidate C is signed by the repository identity with trailers naming worker identity, run and result digest; its tree equals recomputed B plus change set. A trusted reviewer, neither untrusted-class nor the producing identity, reviews exactly C. Acceptance binds to C (K1), never to patch equality. Executing C stays in R-VERIFY; before acceptance an untrusted candidate is never pushed where CI would run it with secrets.
5. **Rework and integration (board ownership).** Changes-requested findings return via the board; the next round uses admitted candidate C. A remote worker gets a signed task letter and continues its donor-side session with a freshly materialized workspace; the old workspace is removed only after complete-content export discharge or an explicit per-act waiver. An export refusal produces no C: use the bounded same-workspace repair path above, or start a new admitted round on the last admitted base after disposition. A local agent gets a new run from C with findings in its task snapshot. The next export yields C2 on C. Questions use ordinary letters/outcomes. The accepted exact head integrates by signed fast-forward (K1/K3); a moved base uses the board's ordinary refresh and re-review. Code becomes a commit only in our repository and lands only through this existing board path.

RWP v2.1 §8 change-extraction and §10 orchestrator gates are adopted; the approved child-UID executor exports instead of a harness reading a container volume. Optional immutable read-only object sharing still would need provenance/access/retention publication. R-TRANSFER settles source/result-transfer ownership; only its unpublished formats/interlocks remain open (§14, question 15).

## 8. Firewall per account (v1)

Figures [M-UM1: privileged components](../diagrams/components.puml) and [M-UM2: provision, retire and recovery](../diagrams/provision-retire-recovery.puml) label the static range rule, v1 adapter, evidence refusal and denial lifetime. The existing apply/applied-state sketches below cover trusted proxy-bound agents only; the zero-egress encoding would need publication (§14, question 18).

```
fw.apply  args: { generation, profile_ref, profile_digest, proxy: { port } }
fw.remove args: { generation }
```

- **Intent (R-NET-TOOL).** Agent and workplace accounts have no general internet. Trusted local agents reach only model-provider endpoints through the bound profile proxy, with vendor names in the proxy allowlist. Workplaces have zero egress: no proxy destination, including no loopback. Unix-domain sockets are outside packet filtering but only the declared platform socket set is reachable (R-SOCKETS); reachability is qualified, never assumed from authentication alone.
- **Static range deny (R-RANGE-DENY, from v0).** The installer places a default-deny rule for agent/workplace UIDs 30000–59999 in the helper-owned parent anchor/table before any agent account exists, independent of per-account `fw.apply`. v0 admits only platform proxy listeners; v1 narrows per account to the bound profile or zero egress. v0 and Slice 0 refuse the untrusted class. Linux uses nftables `meta skuid` range rules with counters/logging covering every protocol. macOS uses pf `user` range rules plus the launcher-applied sandbox for traffic outside TCP/UDP. Verification proves no earlier `quick` rule in any anchor (including host ingress anchors) matches range traffic on any interface, including loopback and tunnels. An active probe from a dedicated test UID runs at install, every service start and on the verification schedule (§8.1). Failure is an incident: enforced readiness drops. Rule/probe encoding and schedule are unpublished (§14, question 18).
- **macOS:** one `pf` anchor per account under a helper-owned parent anchor using `user <uid>` rules; the parent anchor's position in the main ruleset and pf's enabled state are verified on every apply. **Linux:** one helper-owned nftables table with `meta skuid <uid>` rules.
- **Support matrix.** pf associates only TCP and UDP traffic with an account. v1 states, per OS release, which of these it enforces with evidence: TCP and UDP over IPv4 and IPv6, loopback and external destinations, DNS and QUIC, sockets created before the rules, and the interaction with system rules and existing states. Anything an unprivileged account can do outside that matrix (other protocols, for example) needs an additional restriction applied by the launcher (such as a sandbox profile that limits socket creation) or makes the tuple unsupported (`fw_unsupported`). No profile is reported as enforced until its whole matrix has evidence.
- **Order.** The static range deny precedes account creation and remains after retirement. For an account whose profile requires enforcement, per-account narrowing/denial is installed in the same locked operation that activates the account, before the first launch; it is removed only at the end of retirement (§4.4). Rule changes for a running account flush that account's existing states.
- **Proxy / served-policy check (R-NETBIND, trusted proxy-bound agents).** The [network-profiles N15 revision of 2026-10-13, item 5](https://github.com/relux-works/curator-network-profiles/blob/main/spec/network-profiles.md#n15-platform-hosts-a-machine-owned-binding-and-service-accounts-swarma-v1) owns the listener evidence: `account_generation`, `profile_ref`, `service_generation` and `served_policy_digest`. There is one proxy listener per bound account generation, bound to its profile; the account row admits only its own port, already carried by `fw.apply` as `proxy.port`. `fw.apply` verifies that the listener evidence matches the target account generation, pinned profile and listener service generation, and that `served_policy_digest` equals the digest bound for that profile; ownership alone is insufficient. `served_policy_digest` covers allow entries, caps and the dial-guard version `dial-guard/1`, owned by N15 item 11. The canonical relation between `profile_digest` and `served_policy_digest` remains unpublished until the network-profiles contract appendix defines it; they are not assumed equal. Bind evidence to port and `service_generation` for the listener lifetime; reload/port reuse cannot silently widen bound accounts. Failed/unreadable/mismatched evidence admits no apply success or enforced applied-state publication. A synchronous proxy query follows R-LOCK (§4.6); staging outside the lock leaves the generation in flight and inactive for launch. Verified enforcement/applied-state publication and account activation commit together under the lock after revalidation, never activation between query and commit. For trusted agents the allowlist holds only the bound proxy destination; workplaces have none. The existing proxy-bearing sketch does not define the unpublished zero-egress apply encoding (§14, question 18).
- **Applied state (trusted proxy-bound agents).** After a successful apply the helper publishes a root-owned, world-readable record per generation: `{ generation, uid, profile_ref, profile_digest, proxy: { service_generation, port }, firewall_generation, applied_at }`. The broker matches leases against this record (broker §5.5), never against a claim from the agent's own process.

**Binding location (R-NETBIND).** A root-owned, agent-readable machine policy beside `etc/user-manager.json` maps the admitted Curator profile identity (name **and lock digest**) to exactly one network profile ref/digest. R-NET-TOOL 6 forbids binding `direct` or `external-http-proxy` to any account on a platform host, trusted or untrusted: `direct` is unbounded and an external proxy cannot publish served-policy evidence. Both kinds and cooperative profiles remain for operator machines without the platform. Workplaces have zero egress and no profile binding or listener. The proposed profile kind `platform-proxy` belongs to the network-profiles N15 revision of 2026-10-13, item 5 (linked above); this module references that kind without defining its schema. Caller-owned home configuration/text cannot define the bound. The filename/closed encoding would need publication (§14, question 14); no `[bindings.profiles]` table is assumed. The dispatcher resolves at `prepare`, pins ref/digest in `input/1`, and refuses a caller `network` selection that differs. Policy/catalog drift between admission and apply refuses rather than changing canonical effect arguments. This reuses grant `profiles` narrowing; no new grant dimension.

**Exec selection in the same protected policy (R-EXEC).** Beside the R-NETBIND entry, a machine-owned relation maps the admitted Curator profile identity and lock digest, intersected with placement and admission-class minimums, to one exec-profile identity and its immutable resolved policy-body digest. Caller text and caller-home configuration are never its authority. The dispatcher resolves it at `prepare`, pins identity and digest in `input/1`, and refuses a caller reference outside the relation. Policy drift at start refuses rather than substituting a body; retry and recovery retain the pin. The launcher verifies the resolved digest and applies the pinned profile before child code, alongside existing class/host/qualification checks (§7). Workplaces default to the narrowest entry; interpreter-bearing use requires an explicit per-placement entry and complete invocation qualification. Grant `profiles` narrows this relation transitively; no separate service, selectable-set policy or new grant dimension is added. Relation/pin encoding and drift refusal representation remain unpublished (§14, question 19).

**Existing-allocation re-apply (proxy-bound agents).** A journaled dispatcher effect applies pinned/narrowed policy to an existing allocation without recreating its account: `fw.apply` has its own effect ID/exact arguments, separate from E-rebind's broker binding replacement (R-REBIND). Revalidate served-policy evidence, flush account kernel states and have the proxy drop or re-check old-policy sessions before certifying new enforcement. Partial/unknown results keep relevant admission/delivery closed with original evidence reconciled. A kernel reload alone is not success; proxy ordering/digest proof/recovery would need joint publication (§14, question 14).

Per-account watcher freeze is outside v0. Its v1/S2 package must publish dominance over stale re-apply, release/version semantics and `fw.apply`/`fw.remove` outcomes (§14, questions 18, 21); this general re-apply description supplies none of those guarantees.

**Workplace hard rows (R-WORKPLACE, R-NET-TOOL).** Before activation qualify denied loopback TCP/UDP over IPv4/IPv6 with no exception, external egress, DNS/resolver bypass, QUIC and existing sockets/states. Linux uses a per-execution network namespace without external interfaces and restricts address families to Unix sockets. macOS uses a sandbox profile denying network plus per-UID denial. Both mechanisms require qualification. The declared Unix-socket set must equal the reachable set (R-SOCKETS); broker, dispatcher and host also refuse workplace principals lacking configured roles. SSH relay grants no role there. Job/standing-runner lifetime and concurrency stay gated (§14, question 11).

**Web default-off (owner decision 3a, R-NET-TOOL 4).** Internet is a tool of the agent loop, not account network access. The design works without web access: by default the donor's loop reaches only its model-provider endpoints and our host, and our environment has no internet. No search or fetch tool is offered by default; CIP-0008 lockdown keeps provider-side search disabled and no donor-side web server runs. Web content mixes outside context with the environment's own context and invites injection. A remote workplace has only its SSH connection; its worker loop remains on the donor.

**Task resources (R-NET-TOOL 4a).** Tasks carry the resources they may need: fresh documentation, API references, specifications and examples. The trusted side gathers and attaches them as board resources; a remote worker receives them as attachments of the signed task letter. The platform materializes them read-only next to the workspace, with their digests in the plan. They are data, never instructions. A worker needing more asks through an ordinary letter or outcome; the trusted side fetches, checks and attaches, and the worker never fetches. Caps, resource/attachment formats and exact plan encoding are unpublished (§14, questions 15, 18).

**Opt-in web options (R-NET-TOOL 4b).** All web options are default-off, granted explicitly per identity for the trusted circle only, never for the untrusted class. The trusted circle is our own agents plus remote workers admitted to it by an operator act at admission (§3). Membership enables donor-side opt-ins only and never relaxes workplace zero egress, the exec profile, transfer or review. The following are design options with unpublished formats (§14, question 18):

- **Provider-side search:** only a qualified tuple proving provider execution with no local fetch; for remote workers this needs a CIP-0008 tuple change.
- **Donor-side MCP server for remote workers:** shipped by the platform, design label `swarma-web`, with donor consent at `init`. It runs under its own donor-side identity in variant B or its own sandbox profile in variant C, never in the harness identity (provider-only egress) or bridge identity. Its egress is only the search provider's API endpoints. Its donor-owned search key stays in that identity, or in the donor's Keychain or a 0600 file in variant A. The key never crosses the channel, enters a `swarma-rb/1` frame/package or becomes requestable by the project. It never fetches arbitrary URLs from the donor's address; results reach only the donor model as tool results.
- **Platform web-tool service for local agents:** default-off and available only to explicitly opted-in trusted-circle identities. It runs in its own service account with its own egress row and profile-bound listener (§8.1), holding the key outside agent accounts, with an allowlist, rate limits and logs. Agents reach it only over a declared Unix socket with peer-UID admission and a grant, never TCP; workplace principals are not admitted. The grant/socket interface and concrete principal remain unpublished.

Dependency downloads occur only in R-VERIFY runners under controlled egress (R-NET-TOOL 5). Both model-provider proxies and runner dependency egress require host/port allowlists, the private/metadata dial guard `dial-guard/1`, per-identity rate/connection/daily-volume caps and logs. The guard and fixed refused-port set belong to the [network-profiles N15 revision of 2026-10-13, item 11](https://github.com/relux-works/curator-network-profiles/blob/main/spec/network-profiles.md#n15-platform-hosts-a-machine-owned-binding-and-service-accounts-swarma-v1); its values are not restated here. RWP's egress service is a candidate implementation. These proxies belong to the network-profiles owner N15; this spec references rather than specifies them.

**Socket and deployment qualification (R-SOCKETS, R-SHARED).** A test-UID probe on each host proves reachable Unix-domain sockets equal the declared platform set: container runtimes, the tailnet daemon, other users' session daemons and every other socket must be unreachable. A host admitting the untrusted class runs no shared message server, ingress/reverse proxy, media server or operator session daemon. Platform services themselves are not shared services. These are admission/deployment qualification rows, not permissions inferred from service names (§12).

### 8.1 Service-profile rows (R-SVC-EGRESS)

Service rows are a v1 capability beside agent rules, in the same helper-owned pf anchor/nftables table. Installer/operator apply/remove authority extends to service generations (§3); dispatchers cannot alter them. The closed deny-all/service-profile argument form is unpublished (§14, question 12); the agent `fw.apply` sketch grants no invented members/operation. Root helper/launcher share UID 0 with host services and get no per-UID row; a root process sandbox is a separate qualified mechanism. This later v1 prerequisite does not disable the earlier software-root slice.

| Service account | Egress policy / qualification prerequisites |
|---|---|
| `swarma-dispatcher` | Deny-all, including loopback TCP/UDP and direct DNS; Unix-socket control only |
| `swarma-session-host` | Deny-all, including loopback TCP/UDP and direct DNS; Unix-socket control only |
| `swarma-credential-broker` | Only its own verified network-profile proxy listener. Vendor-name allowlist lives at the proxy, never rotating/shared-IP kernel endpoint rules. Login/refresh qualify explicit proxy variables for approved Codex executable, observed authentication endpoint set, proxy honored and no direct fallback. `credential_binding` endpoints are not authentication-endpoint evidence |
| Trusted profile proxy service | Proxy-enforced vendor/host/port allowlists, no mail ports, private/metadata dial guards, per-identity rate/connection/daily-volume caps and logs (R-NET-TOOL, N15). Qualify resolver/listener lifecycle; no arbitrary-destination or deny-all claim |
| Platform web-tool service for local agents (default-off design option; trusted-circle opt-in only) | Own service account, own egress row and own profile-bound listener; only that listener port is admitted by its row. Agent ingress only over a declared Unix socket with peer-UID admission and a grant, never TCP; workplace principals refused. **Scheduled verification.** The installer owns a root-controlled service-policy verification schedule separate from metadata `archive.sweep`. Verify every service row, the static range deny and its active test-UID precedence probe (also at install), parent-anchor placement/enabled state, kernel states, listener/policy evidence and DNS restrictions at every service start and periodically thereafter. Missing/mismatched/unreadable enforcement is an incident: drop affected enforced readiness, hold new authority and report it; use R-MAINT recovery controls and R-FATE for any required stop, never an implicit unit-wide execution kill. Concrete interval, bounded verifier entry point and response ordering would need publication (§14, question 12). Periodic checks have a detection window; no continuous-enforcement claim. Proxy outage remains the broker's transient refresh failure/backoff dependency.

**DNS clause.** Per-UID packet rules cannot establish isolation when DNS leaves as macOS `mDNSResponder` or Linux `systemd-resolved` via `nss-resolve`. CONNECT-proxied accounts need no local resolution; the proxy resolves. Deny local resolver access through a qualified launcher/service-unit sandbox (macOS resolver Mach lookup/Mach-XPC paths; Linux resolver socket/namespace paths). DNS and intermediary bypass need explicit evidence rows. Unqualified resolver restriction never yields enforced readiness. Allowed vendor/carrier destinations can carry data; bounded egress is not a no-exfiltration proof.

### 8.2 Read-only usage sampler (R-WATCH)

The sampler collects per-UID CPU, memory, process count, home disk usage, network counters and refused-connection counters, including mail ports. It is read-only, has the least privilege the OS requires, runs as root only where required and holds no other authority. Thresholds are per admission class. Before any automatic action, collection-time attribution binds a sample to its observed generation, boot and sampling interval, revalidated against the current generation under a stable ledger view. Baselines never cross generations or boots; stale, reuse/reboot-spanning or unverifiable samples are discarded, never retargeted. The encoding and platform qualification remain open (§14, question 21).

**v0/S0a scope: stop, hold and status.** On a hard threshold the watcher requests a journaled dispatcher `exec.stop` for the affected account and the dispatcher's published admission hold. It never kills without a journal, restarts an allocation or triggers manual R-ALLSTOP. A stop progresses independently of notification and any later network effect; unavailable dispatcher/stop evidence remains unresolved in status, never confirmed containment. v0 offers no automatic per-account egress-freeze guarantee: the static range rule is not a substitute, and hold/stop cannot retract delivered tokens.

**v0 alerts are status-only.** The threshold crossing, requested hold and stop, confirmed absence or unresolved results are journaled and visible through authorised status reads via `swarma-observer`. Operator detection uses those reads; v0 promises no phone notification or delivery bound. Containment never waits for alert delivery. The inbound phone operator-act channel does not supply notification authority. An enabled later alert route would need an owner, bounded durable delivery/retry/failure status, rate-bounded typed content without agent-controlled strings, and qualification; it grants no operator mutation authority and no new service egress (§14, question 21).

The per-account freeze lifecycle is v1, with the S2 contract package. Dominance over stale re-apply, authorised release separate from restart, versioned effects and `fw.apply`/`fw.remove` outcomes stay open; this revision specifies none of them. Thresholds, sampler/status encodings and the later alert contract remain unpublished.

### 8.3 Node-wide emergency stop (R-ALLSTOP)

One operator narrowing act requires authentication and one confirmation, via the phone path once its helper transition is published or the existing authenticated terminal fallback; it is refused inside agent sessions. The operator command fans the same signed act, act identity and canonical content directly to each service's operator intake. Every receiver independently verifies and journals its part idempotently under that act identity; per-service unavailable results remain unknown. This is the required delivery contract, not a published wire/operation encoding (§14, questions 17, 22).

**Independent progress and ordering.** The dispatcher sets its hold at act admission without waiting for downstream calls. Independently and promptly issue the user-manager range deny-all, broker lease/renewal freeze and session-host delivery closure/bound-board snapshots; initiate account stops with bounded parallelism immediately after issue, without waiting for containment acknowledgements. The user manager journals termination as receiver; the dispatcher initiates its E-stops when available, and the operator helper path initiates generation-scoped stops under the act when it is unavailable. Direct cuts and helper stops therefore progress during dispatcher absence, crash loops, unready state or maintenance swap. The operator command reports and retries each part. No offline writer of dispatcher state or writable hold file is introduced: its hold/journal part remains unknown until that service returns and reconciles under exclusive ownership. The broker part can remain unknown while valid helper stop evidence exists; neither blocks the other's progress. Already delivered tokens retain their vendor lifetime.

**Receiver fence before inventory.** At act admission the user manager persists a root-owned all-stop mark under the shared transition lock before scanning any generation. The launcher checks it under that lock and refuses every physical start, including materializers/exporters and already-issued calls. The same mark closes `user.create` and generation activation, including `fw.apply` activation. Reconcile already-issued create/launch intents and establish an authoritative closed-create and account-process-ingress frontier before any absence is final. Keep that fence through classification, observation, recovery and retry; a pre-fence scan alone is insufficient. Fence/frontier persistence, ingress coverage and intake encodings remain activation gates (§14, question 22).

| Generation inventory under the receiver fence | Required user-manager outcome |
|---|---|
| Authoritatively never launched; complete generation-scoped launch coverage and no pending launch | Record fresh, qualified, generation-bound zero-account-process evidence as this act's absence result. No execution ID, start receipt or ordinary stop API is invented. |
| Receipt-backed execution | Existing latest-receipt interlock and §4.7 account-wide termination/quiet-period confirmed absence; retain original effect evidence. |
| Pending/ambiguous launch, lost/missing receipt history, or conflicting process evidence | Reconcile original effects and retain unresolved obligations; missing evidence is never proof of no launch or absence. |

An unexpectedly populated receipt-free generation stays pending for explicit operator reconciliation: no narrowly authorised receipt-free signalling contract is published here. Do not signal an unfenced UID, reuse an old receipt, manufacture a dummy start or automatically retire a standing allocation. `user.list` and `effect.observe` alone do not supply fresh all-stop absence. This never-launched case also applies with a healthy dispatcher and remains a distinct acceptance case from dispatcher-unavailable delivery.

**Whole-act recovery.** Each durable service part, including the dispatcher's hold and reconciliation, must be known before the act counts as successful or reopening begins. Partial/unknown results are incidents and keep admission closed. The dispatcher reconciles operator-initiated stops without relaunch, releasing claims only on confirmed absence. Explicit content-confirmed recovery names the stopped set and per-session restart scope; clearing one closure condition leaves the others in force, with hold cleared last. Recovery does not start anything: existing owner lifecycle authorisation or fresh admission, host permit/fence/native-lock checks and every independent readiness gate still apply. Act, inventory/absence evidence, per-service records, recovery scope and phone-to-helper transition remain unpublished (§14, questions 17, 22); no new helper operation, wire member or refusal code is assigned.

## 9. Grant verification (v2)

In the platform design the helper is a handler process that independently limits authority. v2 checks, for every request, a grant chain to a configured root that authorises the action on the concrete target in the current time window and is not revoked, and verifies that the caller is the grant's subject (for example by a signature of the subject key over the request). A valid chain presented by someone else is not authority. The role policy of §3 remains as defence in depth.

**OWNER DECISION NEEDED — v2 signed requests (contract W3):** adopt an explicit component-specific format, or a versioned shared adapter; then publish the signed domain/version and canonical bytes. D-WIRE-NAMES supplies the naming rule, not a signature grammar. No concrete signed-request tag is specified here; v0/v1 continue to authenticate the configured sudo caller and refuse grants.

## 11. Installation

The installer places both binaries, the root-owned configuration (callers and roles, quotas, UID and GID ranges, home roots, quarantine and archive directories, the approved executor list with digests, proxy service accounts), the ledger, journal and audit directories, the exact-path/no-argument sudoers rules (§2; launcher rule for configured dispatchers only) and, from v0, the helper-owned parent firewall anchor/table and static range rule before any agent account exists (R-RANGE-DENY, §8). It runs the dedicated test-UID active precedence probe at install, every service start and on its verification schedule; failure is an incident and drops enforced readiness. v1 adds per-account narrowing; v0 admits only platform proxy listeners and refuses the untrusted class. It creates the protected service-class accounts `swarma-operator` and `swarma-observer` through the user manager under configured installer authority (§4.3), pins the former as the helper operator UID and broker operator/account owner, and installs protected operator binaries/configuration. Neither account ever hosts a harness session. Operator authority and keys MUST NOT be provisioned into a person's interactive/session account. For R-SVC-EGRESS it installs every service row and a root-controlled service-policy verification schedule separate from the metadata-only timer (§8.1). For R-NETBIND and R-EXEC it installs the existing root-owned machine binding policy beside `etc/user-manager.json`, including the placement/class-bounded exec selection and immutable body-digest relation (§8); dispatcher prepare pins and launcher verification are required before the first profile is activated. Workplace relay/backend installation stays gated (§14, question 11). Operator/observer service egress rows would need publication before their v1 enforced readiness (§14, questions 12, 17).

**Phone-first operator entry (R-OPERATOR).** The operator device key is hardware-backed and presence-gated: it lives in the phone's secure element (Secure Enclave or StrongBox), never leaves the phone, and is usable only after biometric confirmation. The phone app connects over the tailnet by SSH to `swarma-operator`, using that key only. The entry has no shell: a forced, narrow **operator command** accepts operator acts only. Its binary name, wire format and exact sshd configuration are unpublished (§14, question 17); no general command execution, password SSH entry or harness session is admitted.

For every act, the app shows the exact content (who, which actions, until when); the phone signs a signed operator record over that one act's canonical content. The machine verifies it against the pinned phone key, bound to that act so the signature cannot be reused for another act. Widening acts require authentication plus explicit content confirmation; revocation requires a single biometric confirmation (§3). The operator device key is one admitted signer where a signed operator record is already named, including `team/1` and standing retirement. The signature domain and canonical bytes are unpublished. No new hardware beyond the operator's phone or signature-algorithm change is mandated; compatibility with the broker v0 root/signature format would need joint publication before activation.

**Terminal fallback and reads.** From a computer, the terminal fallback uses authenticated `sudo` into `swarma-operator` with a password, no `NOPASSWD` and `timestamp_timeout=0`, and performs narrow operator commands under the per-act gates in §3; it works without the phone. The helper operator rule remains authenticated and non-cached (§2). Reads of status, grants, accounts and bindings go through `swarma-observer` without confirmation and confer no mutation authority. Key enrolment, rotation and phone loss remain open, with terminal re-enrolment under this fallback as the proposal (§14, question 17). Loss of the operator account/root authority follows the broker's fenced root-replacement procedure, never a key restore into an account hosting sessions.

R-TIME requires an authenticated or operator-controlled time source (for example NTS) and the common platform time-confidence policy. Broker and dispatcher each durably watermark authority: expiry at `max(now, watermark)`, `not_before` at `min(now, watermark)`; never advance on untrusted time, reset only by explicit operator act preserving genuine expirations. Their own specs own this bookkeeping. Expiry-driven destruction additionally requires boot-inclusive monotonic lifetime evidence (§4.4.1). Unconfirmed boot time or a clock anomaly holds time-driven destruction/reclamation and new authority under the common policy; explicit stops/operator retirement remain available. Tolerances, confidence/incident encoding and restart accumulation would need joint publication (§14, question 16).

R-CEILINGS qualification publishes each host's OS-release capability matrix; infrastructure installs the Linux untrusted kernel baseline and the platform verifies it. R-SHARED excludes shared services beside untrusted work. R-ALLSTOP installs the receiver fence and independently delivered operator parts in §8.3; the authenticated terminal path remains available without the dispatcher, and phone-to-helper activation stays gated. Every durable part is required before whole-act recovery, with no automatic restart.

Uninstall refuses while managed accounts exist unless an operator forces it.

- launcher: unapproved executor, digest mismatch, retiring generation, another dispatcher's generation, `cwd` escaping the home, no descriptor above 3 reaches the executor, supplementary groups cleared, root cannot be regained;
- R-FD3 qualification on each platform: concurrent launch/stop/retire, generation exclusion through receipt and completed UID/GID drop, verified executable handle retained through exec, maximum admitted plan completely staged and immutable on read-only FD3, interrupted staging and bounded cleanup, abort after receipt/drop, exec failure, and no internal handle in the executor (only 0–2 and FD3); a pipe alternative also requires qualified capacity/feeder/deadline/cleanup ordering;
- R-OBS qualification: all six observation states, original-principal/operator access and refusal of other principals, digest/operation mismatch, serialization with mutation/recovery, crash before intent/during effects/after result persistence/before acknowledgement, rollback/removal tombstones, current state on old success, reconciliation after caller/grant expiry, expired/missing/unreadable/partial evidence `unavailable` rather than `not_recorded`, contradictory evidence, and no observation-induced create/relaunch;
- Local retirement: direct operator retirement during broker outage/refusal/fenced restore, durable pending unbind obligation and later reconciliation, stale binding and UID reuse without inherited authority;
- Account-wide stop: signal/verify identical account-wide sets including `setsid`, double fork, `nohup`, OS/pre-receipt processes and backward clock steps; absent root with escaped children, PID/UID reuse, old receipt after successor, success replay without signalling, quiet-period absence and unkillable processes; cron/at/lingering/session-scope/launchd denial on each OS;
- R-OUTCOME: every create/launch/stop/retire table row; `processes_remain` progresses under same ID/canonical grace, changed grace conflicts, old successful stop cannot signal successor, pre-admission retry after authority expiry/revocation refuses new authority, transport uncertainty never fabricates pending intent;
- Bounded cleanup: large/deep/wide quarantined trees with unrelated launch/stop/observation, bounded recovery/batches and lock yielding, repeated deletion failures, crash between batches, safe resume with measured fair progress, retained quota/UID reservations and refusal of activation/reuse before full cleanup; no metadata-timer authority widening;
- R-GEN: entropy failure/collision handling, fresh generations after cursor rollback, ledger restore below reader floor, external fence closes all readers before restored bytes, tombstones never resurrect, missing OS account contradictory, pre-restore observation unavailable until coverage, reverse inventory holds orphans. Local whole-machine rollback detection is not claimed;
- R-FATE: each process-class row per OS/selected unit configuration, service stop/crash/restart/replacement, affected execution absence before swap, unaffected survival only for promised backends, old-daemon supervisor and stale-completion writes fenced, no live-supervisor adoption, broker child containment, unexpected death recorded lost;
- R-WORKPLACE: v0 activation refusal, mandatory v1 applied-state/loopback gate, fixed SSH relay reads no worker startup file, service controls outside workplace UID, unauthorized Unix-socket roles refused, job/runner blast-radius qualification; copied cross-account linked-worktree/backlink and inherited Git config/hooks/credential helpers refused, private administration and admitted source/base;
- R-SVC-EGRESS: all service rows' IPv4/IPv6/loopback denial/allow evidence, explicit broker proxy login/refresh endpoint evidence and no direct fallback, ruleset replacement/pf disable/start/scheduled detection and readiness drop, macOS Mach/XPC and Linux resolver bypass, unqualified DNS never reported enforced;
- R-NETBIND/R-LOCK/R-TIME: caller-home/profile-name spoof and network mismatch, policy/catalog drift, served-digest mismatch/read failure/port reuse/reload, re-apply old proxy sessions and partial recovery; stalled unlocked proxy query while unrelated controls run, in-flight activation refusal, stale return under changed fences; trusted/untrusted clock steps, wrong boot RTC/VM resume and monotonic lifetime gate without revived expiry/early deletion;
- v1: the support matrix for each OS release, including denied and allowed destinations, other accounts unaffected, rules present before the first launch and kept until retirement ends, applied state published and removed.
